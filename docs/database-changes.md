# Database changes

Every change to the database, in plain words: one line per migration, newest
at the bottom. The SQL itself is in
`packages/db/prisma/migrations/<name>/migration.sql`. How a migration is
made and the rules it follows: `docs/engineering-standard.md` §5.

**Safe?** says whether going back to the previous app version still works
with this change applied. "Yes" for additions; "Check" means read the note
first.

| 2026-10-28 | `document_numbers` | A new table keeps, for each shop, the last number given out in each kind of document — bills, returns to the supplier, payments — so each counts 1, 2, 3… on its own (shown as BILL-0001, RET-0001, PAY-0001; the prefix is never stored). Existing numbers are kept; each counter starts after its kind's highest number. The app can't delete a counter. Row-level security: each shop its own | Separate document numbers | Yes (a table, a looser unique rule and a fill-in of the counters) |

| 2026-10-28 | `bill_payments` | A new table of payments to suppliers: the bill it pays, a number (PAY-…), the day, the amount in the bill's currency (above zero), how it was paid (cash, bank, KHQR, other), a note, who recorded it, and — once — when it was voided and by whom. | 2026-10-29 | `stock_counts` | Two new tables. Its lines: each item counted, what was on the shelf, what the app had for it when it was typed, and — fixed when applied — what one cost. Stock corrections can now say which count they came from. One draft per shop; counts are never deleted; the app can only change a count's status (once: draft → applied or cancelled), and a count's lines only while it's a draft (the owner deleting a whole shop still can). Row-level security: each shop its own. Nothing is filled in | Count stock as a document: by category, value of differences, continue later on any device, past counts | Yes (new tables and an empty column only) |

The app may set these two, once, and change nothing else on a bill; a bill can never go back to not received. A return always counts as received. Every existing bill and return is filled in as received at its own save time (their stock already went up) | Save a bill before the goods arrive; Received adds the stock | Yes (columns, a check, a trigger, a narrow grant and a fill-in) |
